# Session du 2026-09-18 — tranche 7, fiche 0011

## Objectif

La tranche 6b livrée, Lucas a dit « on continue » : la suivante dans `status.yml` est la 7, le
connecteur MCP distant pour Claude Chat et Cowork, protégé par OAuth. L'issue #7 pose une condition
à toute implémentation : si OAuth exige de conserver des clients ou des jetons, une fiche tranche où
et comment, et elle est actée d'abord. Cette session établit les faits et écrit cette fiche.

## Actions

- **Relu à la source, non de mémoire** : la spécification MCP (autorisation, révisions 2025-06-18 et
  2025-11-25 ; transports Streamable HTTP), la documentation des connecteurs Claude
  (authentification, construction, authentification différée), les paquets du SDK TypeScript sur
  npm — jusqu'à extraire les archives `@modelcontextprotocol/server` 2.0.0 et `core` pour lire
  leurs signatures —, et l'API de contenu de GitHub.
- **Les faits qui commandent le choix** :
  - le serveur MCP est un *resource server* : métadonnées RFC 9728 **MUST**, 401 à
    `WWW-Authenticate: Bearer resource_metadata="…"` **MUST**, audience du jeton vérifiée **MUST** ;
  - le serveur d'autorisation : OAuth 2.1, métadonnées RFC 8414, PKCE `S256` annoncé, redirect URI
    comparées exactement, rotation des jetons de rafraîchissement pour les clients publics
    **MUST** ; l'enregistrement des clients se fait par CIMD (**SHOULD**), pré-enregistrement, ou
    DCR (**MAY**, « pour compatibilité ») ;
  - Claude, sur toutes ses surfaces dont Cowork : PKCE toujours, **une seule URL de rappel**
    (`https://claude.ai/api/mcp/auth_callback`), un **identifiant client pré-enregistré** saisissable
    dans les paramètres avancés du connecteur, rafraîchissement réactif avec rotation attendue,
    dix secondes de délai, plage d'adresses `160.79.104.0/21` ;
  - le SDK v2 (2.0.0, publié la veille, lignée stable) sert le MCP en Streamable HTTP par une
    fonction `fetch(Request) → Response` sans état, avec une garde Bearer à vérification injectée,
    et **ne fournit aucun serveur d'autorisation** ; son adaptateur Node dépend de Hono, inutile :
    h3 1.15, celui que Nitro exécute, expose `toWebRequest` et `sendWebResponse`, auto-importés.
- **Écrit la fiche [`0011`](../docs/decisions/0011-autorisation-oauth-du-connecteur-mcp.md)**,
  proposée : cinq options, dont une sous-option. Retenue pour validation : le dashboard est son
  propre serveur d'autorisation, pour un client pré-enregistré — Claude —, authentifié par la
  session GitHub existante ; jetons d'accès signés d'une heure, liés à l'audience ; jetons de
  rafraîchissement tournés, conservés par empreinte en SQLite (migration 3) ; codes d'une minute en
  mémoire. Le critère : la fermeture — un utilisateur, un client, une URL de rappel, connus
  d'avance.
- **Relevé un préalable** que la fiche consigne : le jeton GitHub de production est limité à la
  lecture des contenus ; l'écriture dans `docs/` exige le droit d'écriture des contenus sur
  cairn-wms.

### La fiche actée, la réalisation

- **Lucas a validé la fiche** (« Ok »), et demandé comment obtenir les deux variables : l'identifiant
  client se **choisit** — c'est la valeur qu'il saisira dans Claude —, le secret se génère ; les
  deux vont dans les variables d'environnement de l'application Coolify, avant la fusion, puisque
  `/health` les exigera. Fiche `0011` passée à actée, tranche 7 en développement.
- **Le SDK v2** (`@modelcontextprotocol/server` 2.0.0) et `zod` installés **avec le npm de
  l'intégration** (`npx npm@10.9.4`), la leçon de la tranche 1c ; le paquet n'a tiré ni Hono ni
  Express. Ses signatures ont été lues dans l'archive npm extraite, non dans la documentation.
- **Écrit le serveur d'autorisation**, sans bibliothèque : `mcp-jetons.ts` (JWT HMAC-SHA256 d'une
  heure, vérifié à temps constant, refusant tout autre algorithme ; jetons de rafraîchissement
  opaques conservés par empreinte), `mcp-oauth.ts` (lecture d'une demande dans l'ordre de l'OAuth
  2.1 — client et rappel refusés sur place, le reste renvoyé au client —, PKCE S256, codes d'une
  minute à usage unique en mémoire, métadonnées dérivées de l'origine servie, défi Bearer),
  `mcp-demande.ts` (la demande en attente, scellée dix minutes dans un cookie), les routes
  `/oauth/autoriser` (GET puis POST du consentement, origine vérifiée comme pour les tickets),
  `/oauth/jeton` (code puis rafraîchissement avec rotation), les trois `/.well-known/`, et l'écran
  `/connecteur/consentement` avec les briques du design. Le parcours de connexion GitHub accepte
  un `retour`, limité à un chemin du dashboard.
- **Migration 3** : la table `jetons_mcp` ; `tournerRafraichissement` marque l'ancien remplacé et
  **révoque toute la famille** si un jeton déjà tourné se représente ; purge des expirés avec celle
  de l'historique.
- **Le serveur MCP** (`/mcp`) : `createMcpHandler` du SDK, sans état, servi par `toWebRequest` et
  `sendWebResponse` de h3 1.15 — celui que Nitro exécute. Avant le SDK, la route joue le *resource
  server* : `Origin` étranger refusé, jeton vérifié — forme, signature, expiration, **émetteur,
  audience, client et compte** —, 401 à `WWW-Authenticate` sinon ; écrire sans `docs:write` répond
  403 `insufficient_scope` **au niveau HTTP**, comme Claude le demande pour proposer de
  réautoriser. Trois outils : lister, lire (avec le `sha`), écrire — l'écriture bornée par
  `ecriture-doc.ts` : `docs/`, `.md`, `dev`, message `docs:` composé par le serveur, taille, `sha`
  du contenu lu exigé pour une mise à jour (409 sinon, 422 sans `sha` sur un existant).
- **Le mode fictif** connaît le connecteur (`client-fictif`, secret tiré au hasard) et le faux
  GitHub accepte les écritures de contenu, en mémoire, avec la sémantique du `sha`.
- **Éprouvé** :
  - 41 tests nouveaux — jetons (signature retouchée, algorithme `none`, expiration, contenu
    incomplet), OAuth (chaque refus de la demande, PKCE, codes, métadonnées), écriture (chaque
    refus, Octokit simulé), rotation en base ; 351 tests au total. Un test existant a été mis à
    jour : migrer une base restée en version 1 applique désormais deux migrations ;
  - **un parcours de bout en bout** contre la pile fictive, 34 vérifications : découverte, refus
    sans jeton et jeton bidon, client inconnu refusé sur place, PKCE absent renvoyé au client,
    session exigée puis consentement, origine vérifiée, refus → `access_denied`, code émis, PKCE
    faux → `invalid_grant` et code consommé, code rejoué refusé, jetons délivrés, `initialize`,
    `tools/list`, lecture, **écriture hors `docs/` refusée**, mise à jour sans `sha` refusée,
    écriture puis relecture, création, rotation, rejeu → famille révoquée, consentement en lecture
    seule → écriture 403 `insufficient_scope`, autre compte renvoyé à la connexion ;
  - **le test de fumée** sur l'image construite, contre le vrai cairn-wms en lecture : les mêmes
    refus, le parcours complet jusqu'à `lister_documents` sur l'arbre réel, la rotation, le rejeu,
    et `/health` qui signale `connecteur: client-absent` sans configuration.
- **Capturé l'écran de consentement**, sur données fictives, deux thèmes, deux largeurs — puis
  refait sur l'image exacte de production lancée sur le poste, avec une demande en attente : ce
  sont ces captures-là qui sont jointes.

## Points ouverts

- **Le rafraîchissement n'a pas encore été observé avec le vrai client** : le premier jeton d'accès
  dure une heure ; Claude devrait le renouveler seul, comme sa documentation le décrit et comme le
  test de fumée l'a joué. À constater à l'usage — un « Connecter » qui réapparaîtrait au bout d'une
  heure dirait le contraire.
- **La permission d'outil de Claude se remet parfois à zéro** après une mise à jour du serveur ou
  de l'application (issues connues côté Anthropic) : si Claude redemande « Toujours autoriser », ce
  n'est pas le connecteur.
- **Claude Code reste hors du connecteur** tant que le CIMD n'est pas ajouté (fiche `0011`).
- **La protection de `main` n'exige que le contrôle « Contrôles »**, pas la publication de l'image :
  une fusion trop rapide fait échouer le déploiement, sans dommage mais avec une relance à la main.
  Exiger aussi « Construire, éprouver, publier » avant la fusion réglerait la question — un réglage
  du dépôt, à décider par Lucas.
- **Le dashboard a livré tout ce que son cadrage prévoyait, sauf la tranche 8**, mise de côté.
  Ce qui viendra ensuite n'est pas décidé : la reprise de la 8 quand cairn-wms en aura besoin, ou
  ce que l'usage du connecteur et du dashboard fera apparaître.
- **La capture du consentement vient de l'image de production lancée sur le poste**, avec un
  client d'épreuve : le vrai consentement de Lucas a eu lieu une fois, dans son navigateur.
- **La révision de spécification que le SDK v2 implémente** (2026-07-28) est plus récente que celles
  que Claude déclare prendre en charge (jusqu'à 2025-11-25) : la négociation de version devrait
  suffire, à éprouver avec le vrai client.
- Points antérieurs inchangés : Node 24 sur le poste contre 22.23.2 dans l'image ; l'épreuve
  visuelle ne tourne pas en intégration continue.
